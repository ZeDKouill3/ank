The lane arithmetic of GRAPH option B, cut out as pure code so that every
shape can be pinned as a literal on Windows before a terminal is involved,
exactly as TASK-9f11c7c06f72 did for the first layout.

**What changes against the layout the view draws today.** The first layout
draws every connector on the row of the node that leaves it: a tee or a
corner into a lane that already runs, so a merge happens where the edge
starts. The human saw both and chose the git log --graph shape: a lane is
opened to the right of the node (`─┐`, `┬`) and lanes waiting for one blocker
merge on a row of their own just above it (`├─┘`, `┴`), with `┼` where a
horizontal crosses a lane that passes. A task is still exactly one row; what
is new is that rows exist which are nobody's. That supersedes the "one row
per task and nothing else" clause of TASK-9f11c7c06f72 and TASK-643611645dea
on purpose; their criteria stay as they were closed and this one states the
new behaviour.

**The cells move too.** Finished is the filled circle now and open the empty
one, because the thing a finished row has to say is that it is settled and a
filled cell reads as settled; readiness stops being a glyph and becomes the
word on the row (the sibling task on the readiness column), which is why
Ready and Waiting share one cell here. In progress is a pulse of four phases
and this module only knows the phase number: which phase is drawn, and when
it moves, belong to the view and to the clock task after it. Colour is not
this module's and never was (ADR-559eebf5c6f5: the frame with paint and the
frame without it are identical character for character).

**Why the old layout stays standing for one task.** The view's relayout, the
unit seam in view.rs and the pseudo-terminal suite in tests/graph.rs all read
the first layout and its glyphs. Removing them here would put view.rs in this
task's scope, and view.rs is where the readiness column lands in parallel.
So the table grows rather than changes, the new layout is a second function,
and the view task deletes the first when it moves across. One table, more
rows, for one wave.

**Groups are arithmetic as well.** Which tasks are linked to which is a union
over the drawn edges and nothing else; how the groups are ordered on the
screen (alive first, then bigger, then newest) needs `created` and the fold,
which are the view's, so the function here answers the groups and the view
sorts them.
