## Context

Every ratification on this repository is a pull request, and the pull request
is the whole cost. `accept --pr` already automates the eight-line recipe
(ADR-2a63c0c87691); what it cannot automate is the thirteen minutes of CI a
one-file corpus change pays for a test matrix that cannot be affected by it,
nor the merge a human has to come back for. Measured on 2026-10-17: a pull
request touching only `.ank/` runs 13 minutes, 757 of its seconds being the
Windows suite, against two seconds of `ank check`; PR #624, which ratified one
decision, took 3 h 50 from creation to merge after one flake and one rerun;
four of the last five pull requests touched nothing outside `.ank/`.

All of it follows from one fact: the anchor is a commit. A commit cannot name
itself, so the pointer is the history (SPEC-ac4aad6d1edb §3), so `check` walks
`rev-list --full-history` with no path restriction, so CI checks out the whole
history, so a squash loses the anchor and a rebase loses the signature, so the
merge method is load-bearing, so `accept` has to stand on the default branch,
reset it, and carry the commit through a pull request. `check` itself never
looks at the default branch: a `ratify <id>` commit reachable from `HEAD` is
the anchor wherever it was made.

The repository already holds the shape of the answer. A claim is a ref
(`refs/ank/claims/<id>`), a proof may be a ref (`refs/ank/proof/<id>`,
ADR-493471d64ba0: "a statement with no tree to travel in"), and §12 says ank
never commits, "with one exception". What no ref carries yet is a signature,
and a signature is what a ratification is (SPEC-ae044e8ac714 §8).

## Decision

**The file declares, the ref holds the authority.** Every act that binds the
whole repository has a ref: `claims` says who holds, `proof` says what ran,
and `ratify` says what binds. Ank never commits, with no exception.

**The object.** `refs/ank/ratify/<id>` points at an annotated tag object:

- `object`: the blob of `.ank/entities/<id>.md` as `accept` wrote it, which is
  the exact bytes made binding, content-addressed and readable by
  `git cat-file -p` with nothing else;
- `tag`: `ratify/<id>`; `tagger`: git's identity and the instant;
- message: `ratify <id>`, then the lines today's ratification commit carries
  (`constraint+scope: <hash>` or `body+scope: <hash>`, `by: <actor>`,
  `supersedes: <id>` where one applies). The hash stays the short key every
  reader compares; the blob is the long proof;
- signature: git's own, under whatever `gpg.format` the repository uses,
  present when `can_sign` holds and absent otherwise (ADR-964be4d940b2 is
  unchanged: signing is a regime, and every surface says which).

Reproducible without ank, which is what standardises it: `git hash-object -w`,
`git tag -s -m <message> <tmp> <blob>`, `git update-ref refs/ank/ratify/<id>
<tag>`, `git tag -d <tmp>`. Verifiable without ank: `git verify-tag` against
the allowed signers. Signed tags exist since git 2.34, the floor ank already
requires.

**What the file gains.** A commit could not be named by the file it ratified; a
tag written before the file can. `ratified:` keeps the hash, so a reader
without refs still compares what it always compared, and `anchor:` names the
tag object. A lost ref is no longer a mute "unverifiable": `check` says which
object is missing its ref, and `update` restores the ref from an object the
repository still holds.

**The verbs.**

- `accept` writes the blob, the tag and the file, pushes the ref with
  compare-and-swap as `attest --detached` does, and fails at exit 9 with
  nothing kept when the push does not land (ADR-af533e7a3e03). It runs on any
  branch: the ref is a fact about the repository, not about a branch. It keeps
  every refusal it computes before writing (ADR-3b6ba766a42e among them), and
  those refusals are the whole of the review a ratification gets, which is what
  they already were in law: a pull request can reject a branch, it cannot
  un-sign what is on it. `--pr` goes, and with it the branch gate, the reset
  and the recipe. The file lands with whoever's next change, by any merge
  method.
- `check` reads `refs/ank/ratify/*` in one `for-each-ref` and one `cat-file
  --batch`, judges each signature against `signers:` through `git verify-tag`
  with the generated allowed-signers file, caching verdicts by object name as it
  caches commit verdicts today, and compares the anchor with the file. An
  anchor the refs do not carry is sought by the `ratify <id>` commit walk,
  which stays as long as such anchors exist. New outcomes, all signals: a
  verified ref whose file still reads `proposed` (the file has not caught up,
  the same family as a completion ref); a file whose `anchor` names an object
  no ref points at (with the command that restores it); a ref with no file; a
  file marked `superseded` that no ref's `supersedes` names. A tag signed by an
  undeclared or retired key is a fault, as a commit is today.
- `context` and `scope` serve a constraint as binding when a verified ref
  matches the constraint and scope of the file they read, whatever `status:`
  says. That is the sentence that takes the pull request off the path of
  authority. A reader without the refs falls back to the file and sees
  `proposed`: less, never wrong.
- `accept --reanchor <id>` is the one act on an anchor made before this
  decision: it writes the tag and the ref for an entity whose anchor is a
  `ratify <id>` commit, with the same hash, a message naming that commit, and
  a `verified` entry for whoever ran it, because a re-anchoring is a new
  signature by a new key and the record must say so. Nothing runs it
  automatically and nothing in history is rewritten.
- `show`, `find` and `review` say which of the two carried the anchor, as
  ADR-493471d64ba0 asks of a proof.

The change to the format follows ADR-63b59c5c26f7: the specification first
(SPEC-ac4aad6d1edb §3, SPEC-ae044e8ac714 §8, SPEC-93531977642f §12,
SPEC-15a56aeedcfd §7, SPEC-fe809eb257c0 on `accept`), the goldens, then the
code.

## Consequences

- Ratifying is `ank accept <id>`, on the branch you are on, and it is done.
- The merge method stops being load-bearing for any ratification made after
  this decision. The ruleset keeps merge-only while a commit anchor lives in
  the history, because keeping it costs nothing and those commits are what it
  protects.
- A corpus becomes files at a commit plus `refs/ank/*`, verifiable without
  history. That is the property a hub of corpora consumes: mirror the refs and
  the blobs they point at, verify each ratification against the repository's
  `signers:`, serve what binds across repositories without cloning their
  history. A peer corpus (ADR-a1de673043b4) can be verified by its refs rather
  than by its walk. CI's `fetch-depth: 0` stays only for the commit walk and
  for explaining where a dead scope went.
- ADR-6d8736c04cfa keeps everything it says about completion refs and `close`;
  this decision amends only its sentence giving `accept` a branch precondition.

## Limits accepted

- `refs/ank/*` is outside every ruleset GitHub can express: anyone with push
  can delete a ratification ref. Claims and proofs already live with that, a
  squash today has the same effect (a signal, not a fault), and three things
  compensate: the file names the object, a forged ref under an undeclared key
  is a fault, and a hub that mirrors is a second copy.
- A clone that never ran `ank init` and never fetched `refs/ank/*` reports the
  ratification unverifiable until `ank update`. Proofs already behave so. The
  test job of `ci.yml` fetches the refs before `check`, read-only, so a pull
  request from a fork verifies them.
- No pull request shows a ratification any more. The last human look is the
  one of whoever types `accept`, which it already was: the merge re-read
  nothing.
- Two anchor forms coexist in `check` for as long as a corpus holds a commit
  anchor. `--reanchor` is the way out for a corpus that wants one form, and it
  is opt-in by a human because it re-signs.

## Rejected alternatives

- **Keeping the commit and making the pull request cheap**: a CI fast path and
  auto-merge. Worth having on its own and planned beside this decision, but it
  leaves the merge method load-bearing, `accept` pinned to the default branch,
  the history as the only pointer, and a hub obliged to clone history. It
  treats the symptom.
- **A signed blob with a detached signature** (`ssh-keygen -Y sign`) under the
  ref: no git tool reads it, every verifier reimplements the format, and the
  openpgp regime has no equivalent. A tag object is what git already signs and
  verifies.
- **A signed commit object with no parent under the ref**: verifiable by the
  same path as today, but a commit with a tree is a heavier object for a
  statement that names one blob, and git tools present a parentless commit as a
  root, which it is not.
- **Deriving `status: accepted` from the ref alone, with no write to the
  file**: the file would stop saying what the corpus is, and a reader without
  refs would see every decision as proposed. The file keeps declaring; the ref
  is what makes the declaration true.
- **Protecting the refs by a ruleset**: not expressible for a namespace outside
  `refs/heads` and `refs/tags`. Putting ratifications under `refs/tags` would
  make every one a release in the forge's eyes.
