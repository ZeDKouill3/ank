## Context

On 2026-10-13, right after v0.9.1 was published, `ank update` on Windows (npm
route) printed

    installing 0.9.1 over 0.9.0: npm install -g @haksolot/ank@0.9.1
    removed 1 package, and changed 1 package in 1s
    ...\@haksolot\ank-win32-x64\bin\ank.exe did not answer --version after the install

and exited 0. The wrapper was at 0.9.1 with no platform package under it, so
every later `ank` answered exit 9, "@haksolot/ank-win32-x64 is not installed".

Cause, read from the npm debug log: a first attempt minutes earlier, before the
registry served 0.9.1, failed with ETARGET and left npm a cached packument of
`@haksolot/ank-win32-x64` without 0.9.1. The next install resolved the wrapper
from the registry and the platform package from that cache (`placeDep ...
ank-win32-x64@ OK`, an empty version), skipped it silently because it is an
optional dependency, and removed the 0.9.0 one. npm exited 0.
`npm install -g @haksolot/ank@0.9.1 --prefer-online` repaired it.

## What is wrong in ank

`update` treats the route's exit 0 as the verdict. `skills_line` already
notices the installed binary does not answer, but only prints to stderr and
returns `None`, and the verb returns `ExitCode::Ok`. An agent reading the exit
code believes the update landed while the binary is gone. The check that would
tell it is already run; its answer is dropped.

The route is still the authority on how to install (ADR-64f32c74a0f9); this is
only about not reporting success when the result does not run.
